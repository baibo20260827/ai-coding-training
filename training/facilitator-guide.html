讲师运行手册

适用：能力建设负责人、种子导师、协助培训的技术骨干。目标是能够独立组织一次培训，展示完整工程过程并收集可用于改进的证据。

课前准备

提前确认三件事：听众主要想解决哪类任务、他们的起点、课后需独立完成什么。将真实困难与开篇三则虚构案例对照；如果不匹配，记录并改写场景，不把案例当作部门调研结论。

分配讲师、演示操作员/助教和记录人；小班可兼任。确定谁处理环境问题、谁判断业务验收、谁接收课后疑难问题。实际人员和时间写在当次培训记录中。

上课前 30 分钟

检查 操作/判定
文件可用 打开 PPT 并查看备注；打开培训索引、练习和答案；不要依赖外部链接才能继续授课
环境可用 在根目录执行 python3 --version，按案例 README 启动，浏览器能够打开本地地址
正常演示可用 选择一个空日期，建立、刷新、相邻预约、重叠拒绝、取消
检查可运行 执行自动测试和故障演练，理解预设失败被发现时的输出
数据可隔离 使用专用教学数据库和虚构姓名，不清空或覆盖未知文件
AI 工具可用 使用部门准入工具确认能够读取项目；工具不可用时改用已有实现、任务卡和审查练习
时间与记录 打印或打开练习页；留出讨论与演示故障处理时间

共同命令（根目录）：

python3 demo/app.py --port 8765
python3 -m unittest discover -s demo/tests -v
python3 demo/labs/failure_lab.py

启动服务的终端保持运行；另开终端执行测试。关闭服务用 Ctrl+C。不要为了让演示成功而关闭测试或改验收预期。

共同开篇：约 10 分钟

按 00-opening.md讲三个小失败，分别邀请一名听众回答：主管需要什么证据、工程师会补什么反例、新手会写什么验收例子。把回答保存为本次课程问题清单；不记录不必要的个人信息。

在白板或纸上写下三项待解决的问题，后续每个环节回到它们。首次出现术语时用案例解释：需求是要达成的行为；验收是判断该行为是否达到的检查；架构是各部分职责和关系；版本是能区分并恢复的一个状态。

端到端现场演示：约 25 分钟

这套演示使用已实现的稳定教学版本。AI 现场生成属于补充练习，不是顺利讲课的前提。所有操作以案例实际 README 为准。

场景与验收，4 分钟

打开案例需求，请听众指出“同日”指所选日期内不跨日，不代表只能今天。确认单会议室、09:00—18:00、半小时刻度、虚构数据和无审批范围。展示 A01—A08，将已确认的业务例子与实现联系起来。

提出：“客户如果新增审批，是改了哪个范围？”记录为待分析变更，而不是直接开始修改。

设计与边界，3 分钟

打开4A 架构，沿一个预约走过 BA 的业务动作、AA 的页面与服务、DA 的预约和占用数据、TA 的本地进程与文件。仅说明这些关系如何帮助定位影响，不展开框架选型。

指出部署约束和 DfX 目标需要客户确认。当前环境是教学实现，性能规模、组织权限和生产保障不是本次演示已取得的结论。

功能与持久化，6 分钟

选一个没有记录的日期，采用以下固定输入（日期可改，但同一轮保持一致）：

操作 输入 期望
建立预约 2030-01-15，10:00—11:00，学员甲，需求讨论 出现一条记录
刷新页面 重新查看同一日期 记录仍在
相邻预约 11:00—12:00，学员乙，设计讨论 允许
重叠预约 10:30—11:30，学员丙，试验 拒绝，原记录不被破坏
取消与重建 取消第一条，再预约 10:00—11:00 时段释放，可以建立

请学员报出实际结果，由记录人填写。现场实际失败时保留信息，转入排查；不把预期结果写成已观察到的结果。

可重复的小失败，6 分钟

运行 python3 demo/labs/failure_lab.py。按脚本输出解释旧错误、错误修复、弱检查、独立验收及修复后的区别。预设缺陷是教材，不是模型现场真实输出。脚本整体成功意味着它成功识别了预设问题并验证正确行为，不代表有缺陷的版本可以发布。

再运行单元/集成测试，查看持久化、并发、输入边界和 HTTP 行为的实际测试结果。演示中不要把命令退出码代替需求覆盖分析。

交接、恢复与变更，6 分钟

打开案例 README 的备份恢复步骤，说明必须使用独立目标文件恢复并校验，避免覆盖未知数据。由讲师提前做一次恢复演练，保留结果；课堂可按时间选择现场运行或讲解实际记录。

对照周报示例与变更示例，说明实现、验证、客户接受是不同状态。请主管选择一个方案并指出还缺什么确认。

分层练习的组织

主管

以 L5 为主，讲师扮演提出“加审批”的客户，一位学员给出状态判断，另一位复核日期依据。先让学员自主判断再给参考答案。关注是否提出可比较方案、说明依赖、找对确认人、保留质量要求。

资深开发者

以 L3/L4 为主。先要求独立定义用例，再允许 AI 修改。记录委派、实现、审查和返工时间，不从单次练习推导总体提效比例。审查者核对业务预期是否被修改、变更是否越界及缺陷是否被真实复现。

新手

以 L1/L2 为起点。讲师先示范一个验收例子，让学员自己补其余例子。允许同伴帮助启动环境，但要求学员亲手完成操作，并能说出预期与实际。L4 可由导师协助实现，学员负责需求和验收；此时标为“协助完成”。

问题处理与备用路线

课堂状况 处理方式
Python 或启动命令不可用 按案例 README 的系统说明排查；让助教处理环境，学员先完成场景卡，避免全班等待
端口被占用 使用案例支持的其他端口并同步浏览器地址；不终止未知进程
AI 工具暂时不可用 继续用已有应用做验收、用预设缺陷做审查、用任务卡做委派设计，记录工具接入未验证
AI 修改后失败 停止扩大修改，保存复现步骤、检查结果和差异；依据任务卡定位或回到练习副本
客户规则有歧义 把问题送回需求例子，不由讲师临时替客户作决定
时间不足 保留一项完整验收和一次错误发现，把可选进阶练习转为课后任务

收尾与持续支持

收取练习要求的任务卡、结果、检查证据和限制说明。使用参考答案中的评分口径区分独立完成、协助完成、尚需指导；记录的是可观察表现，不是人格或潜力判断。

课后建议用固定的短答疑时段处理可复现问题，具体排期由负责人安排；本项目未自动建立日程。重复问题完善 FAQ，方法变化更新指南，长期通用规则再提炼到 AGENTS.md。

用一次真实低风险任务做迁移练习，指定业务验收人和技术把关人；培训练习通过不自动等于真实业务交付资格。汇总实际问题与改动到改进日志，说明哪些结论已有证据、哪些仍待观察。
