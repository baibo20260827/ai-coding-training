工程师指南：把怀疑转成约束、反例与交付证据

版本：1.1；日期：2026-10-04。适用：具备开发经验的工程师与代码评审者。目标：在合理审查成本下委派任务、识别错误、验证结果、处理回归并接管软件。

先读共同开篇中的虚构案例：相邻预约修好了，重叠预约却被放过，测试预期也一起被改错。合理的质疑应落成独立业务例子与差异审查，不需要预先相信或否定所有 AI 输出。

1. harness 怎样围绕一个任务工作

任务上下文包含需求、现有结构、业务边界、可用工具与权限；执行过程产生小范围变更；自动检查和独立验收提供反馈；状态与恢复材料让下一人接管。AGENTS.md 是工作约定入口，真正的约束还要由代码检查、数据约束、工具权限和人的决策实现。

每个任务用委派审查模板：明确目标、允许修改范围、需求编号、输入输出例子、不能擅自改变的预期、验证与恢复方法。复用AI 任务卡，避免把整个项目一次交给模型后仅等待“完成”。

2. 阅读案例的顺序

先看需求，独立写出 A03 相邻与重叠的判断；再看4A了解职责、数据与运行边界；最后阅读实现和测试。这样业务预期不会仅来自当前实现。

代码契约为本地接口：

操作 接口 说明
查看 GET /api/bookings?date=YYYY-MM-DD 查询所选日期
预约 POST /api/bookings JSON 字段 date,start,end,name,purpose，使用虚构姓名与主题
取消 DELETE /api/bookings/{id} 使用查询返回的标识；不要猜测标识格式
健康检查 GET /api/health 服务响应不等于所有业务验收完成

本地启动：

python3 demo/app.py --port 8765

浏览器访问 http://127.0.0.1:8765。查看案例运行说明确认数据库位置、环境要求、恢复方法和已知限制。服务仅供本机练习，没有登录、审批或生产承诺。

自检：不看实现，先判断“已有 10:00—11:00，新约 09:30—10:00、10:30—11:30、另一天 10:00—11:00”的结果与理由，再对照需求表。若仍不确定，先补业务规则理解，再读代码。

3. 用半开区间建立独立预期

同日区间 [s1,e1) 与 [s2,e2) 重叠，当且仅当 s1 < e2 且 s2 < e1。边界上 11:00 等于已有结束时刻，允许相邻。业务先限定半小时格与 09:00—18:00，再讨论重叠；非法时间不能通过“没有重叠”而被接受。

至少从需求推导五类例子：左相邻、右相邻、部分相交、完全包含、完全位于内部，再补不同日期。测试用例可以由 AI 草拟，但工程师要检查预期的来源及缺失的失败路径。

并发问题不能只靠“先查没有冲突，再写入”：两个请求可能都看到空闲。案例用 SQLite 事务与日期/半小时格唯一约束保护一致性；创建占用中途冲突应整体回滚。数据库约束、代码错误处理和用户反馈必须对应同一规则。

4. 审查什么，怎样控制成本

先看差异是否只为当前任务服务，再看预期变化和数据路径。重点追问：修改了哪些业务假设？是否删除检查或放宽预期？异常路径会不会留下残数据？页面校验之外服务端是否仍执行规则？文档或架构是否被改变？

检查力度跟随影响：小文字修改按显示结果检查；时间规则修改要验证相关边界与原功能；数据约束修改要关注并发、事务与恢复。不为低影响修改机械扩展所有测试，也不因代码少就忽略高后果逻辑。

独立验证首先指依据独立：先从需求推导预期，再检查实现；单人也可执行。另一人或 AI 可以提供审查建议，但建议仍要有可复现依据。实现者与审查者复述同一错误假设并不会增加证据强度。

5. 故障、修复与恢复演练

在项目根目录运行：

python3 demo/labs/failure_lab.py
python3 -m unittest discover -s demo/tests -v

故障脚本是预设教学逻辑，不是模型真实行为统计。读输出时分别判断“故障被检查发现”和“实现通过验收”；脚本整体成功可能表示成功展示了预期失败。不能仅凭退出码为零就认为所有被展示版本正确。

发现问题后先记录步骤、输入、预期、实际结果、代码版本和数据环境；缩小复现，再一次检查一个假设。修复后验证原失败与相关回归。恢复优先在独立练习副本中回到已知版本，按说明恢复教学数据；不要对他人未保存工作或未知数据库直接执行清理。

6. 把新需求交付完整

完成练习 L4：午休 12:00—13:00 不可预约，11:30—12:00 和 13:00—13:30 仍允许。这是尚未实现的练习需求，只在自己的练习副本中修改；当前仓库基线仍允许午休预约。先明确已有预约怎样处理：自学时写出演练假设，真实项目则由业务负责人确认；不默默删数据。分析 BA 规则、AA 校验/提示、DA 旧数据影响、TA 是否变化，再小步实现和验证。获准需求变化后，要审查旧测试中的合法输入是否仍合法，同时保留其原保护目的；具体受影响用例和适配建议见 L4 参考答案。

提交任务卡、差异、实际命令、结果、限制和恢复方法。把相关验收映射回需求，向主管说明还剩什么。若变更会影响已确认日期，提供任务依赖和工期区间，由授权人调整承诺。

7. 工程师完成标准

独立完成 L3、L4 与 L6，能发现一个参考例子之外的缺陷或边界，解释测试预期为何正确，证明旧功能保留，说明当前证据不能支持的结论。真实试点再验证审查/返工时间和总交付成本；当前本地案例不证明生产性能、安全或团队效率收益。

自检三问：预期的依据在哪里？哪个反例能识别错误修复？代码和测试同时改动后，怎样确认不是一起改错？先写答案，再对照参考答案。出现运行阻塞或无法解释的结果，按排查与求助保留复现与假设；不要用反复扩大修改范围代替定位。
