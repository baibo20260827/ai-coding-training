会议室预约：需求与验收基线

版本：1.0；日期：2026-10-03；案例编号：CASE-ROOM-01。

性质：虚构教学案例。 下述业务背景、角色及范围由课程设计者设定，未经真实客户确认。本文是教学实现基线，不构成生产需求或交付承诺。实际执行证据应另行记录，不能用本表替代测试报告。

1. 场景与目标

虚构部门只有一个用于培训的会议室。员工目前在聊天中询问空闲时段，容易看漏已经存在的预约。教学目标是把“看空闲、提交预约、发现冲突、取消后再用”形成可验证的软件行为，串联需求、设计、实现、测试、汇报与变更。

业务目标 G01：查看指定日期的预约，减少重复询问。G02：同一会议室同一时段至多保留一个有效预约。G03：预约结果在刷新与服务重启后仍可查看，取消后时段重新可用。上述目标是教学目标；减少沟通次数等真实收益尚未测量。

角色采用教学占位：使用者“员工甲”，业务负责人“行政负责人”，验收人“行政代表＋技术负责人”，里程碑批准人“项目授权人”。真实试点必须填写姓名、权限和确认依据。

2. 范围、规则与边界

  • 单会议室；浏览器与服务均在本机使用，仅监听 127.0.0.1。采用 Python 3 标准库 HTTP 服务、SQLite 和原生网页。
  • 预约日期由用户选择；开始和结束处于同一日期内，不跨日。“同日”不表示只能预约今天。
  • 时间为本地单时区墙上时间；09:00—18:00，开始早于结束，开始/结束均在半小时刻度。10:00—11:00 占用 10:00 和 10:30 两个半小时段。
  • 区间采用 [开始,结束)：10:00—11:00 与 11:00—12:00 可相邻；与 10:30—11:30 冲突。
  • 所有进入服务端的输入仍需校验；页面控件不能替代服务端规则。
  • 使用虚构预约信息。没有账号、角色、审批、跨部门权限、邮件通知、多会议室、跨时区或生产运维能力。
  • 本地任何能操作此页面的人均可查看和取消预约；这是教学边界，不满足多人共享系统的身份与授权需求。

当前实现的预约输入契约：date 为有效 YYYY-MM-DD 日期，start/end 为 HH:MM 字符串，name 为去除首尾空白后 1—30 个字符的虚构姓名，purpose 为去除首尾空白后 1—80 个字符的主题。预约请求恰好包含这五个字段；缺少、多出或类型不符的字段应拒绝。此契约用于教学代码核对，真实项目的姓名/主题规则需重新确认。

3. 正常与异常流程

正常：选择日期 → 查看预约 → 输入预约信息与时段 → 提交 → 看见成功及预约列表 → 刷新后再次查看 → 取消 → 原时段可以重新预约。

异常：时间非法或缺少必填内容 → 显示可理解的错误且不写入记录；与已有预约重叠 → 拒绝新增且保留原预约；两个请求同时竞争相同半小时段 → 最多一个成功，失败请求得到冲突结果；取消不存在的预约 → 返回明确失败且不影响其他预约。

R01 查看预约 按所选日期显示有效预约 A01：日期甲创建一条，分别查看日期甲和日期乙 甲显示该预约，乙不显示；空列表可理解 G01
R02 建立预约 有效输入产生一条预约 A02：所选日期提交 10:00—11:00 与虚构预约信息 成功，列表出现准确起止时间，能识别待取消记录 G01/G02
R03 相邻与冲突 相邻允许，部分/完全重叠拒绝 A03：已有 10:00—11:00，依次尝试 11:00—12:00、10:30—11:30、10:00—11:00 相邻成功；后两项拒绝，原记录不变 G02
R04 取消 指定记录被取消，时段释放 A04：取消已建预约，再预约相同时间；另尝试取消不存在记录 原记录消失；重订成功；不存在记录的取消失败且无其他改动 G02

每次执行须登记：需求/验收编号、代码版本、实际命令或步骤、数据文件、环境、结果、日志位置、执行人和未覆盖项。验收编号不等同于自动化测试函数名，映射由执行记录补充。

5. 边界例子与判定依据

已存在 新申请 判断
10:00—11:00 09:30—10:00 允许，相邻
10:00—11:00 10:30—11:30 拒绝，部分重叠
10:00—11:00 09:30—11:30 拒绝，包含原时段
日期甲 10:00—11:00 日期乙 10:00—11:00 允许，不同日期
无 17:30—18:00 允许，结束等于营业边界
无 18:00—18:30 拒绝，超过营业边界

半开区间使“前一个结束的时刻”可以成为“后一个开始的时刻”。固定半小时刻度也允许把每条预约转换成若干占用格，用数据库唯一约束维护冲突规则；具体设计见4A 架构。

6. 本期验收与后续变更

教学完成条件：代码可本地运行；A01—A08 有对应验证方式与实际证据；故障练习能稳定出现失败再恢复；参与者能解释检查的边界。测试完成、讲师审阅、学员完成和真实客户接受分别记录。

新增审批属于本期范围外的需求变化，使用变更案例练习评估，不修改本文来伪装成原始要求。真实试点用客户场景模板重新确认背景、角色和边界，不能直接把教学基线当作客户确认结果。
