# 建设方案

版本：1.0。整理日期：2026-10-03。

状态：培训交付包 v1.0 已制作并完成本地工程与材料检查，可进入试讲。组织实施周期和真实试点资源仍是建议，不代表客户已批准的项目基线。

## 1. 目标与约束

让部门有依据地委派 AI、验证结果、处理失败，并培养能够承担交付责任的人。这里采用广义工程 harness：任务规范、项目上下文、开发环境、工具权限、自动检查、反馈与恢复机制。

用户已提出的要求：

- 支持赋能、答疑、指导，形成明确的文档、代码、PPT 等交付件。
- 面向主管、资深开发者和无编码经验者，提供必要的端到端案例。
- 对齐客户需求与场景，规划阶段汇报和进度展示。
- 系统应对需求变更，说明范围、资源与工期影响，支持合理的承诺调整。
- 纳入 4A 架构视图；部署相关仅列客户对齐事项，DfX 仅简述规划、交流和交付方式。
- 使项目能够持续改进，保留稳定规则与改进过程。
- 整个培训以三类受众的主要困难和典型小失败开篇，帮助听众快速进入状态。

两层结果分别验收：能力建设项目的产物与学习效果；真实软件试点的客户价值与工程交付。

## 2. 受众、用途和考核

| 受众 | 重点 | 能力证据 |
|---|---|---|
| 部门主管 | 进度、风险、人才、工具依赖、交付责任 | 根据成果与证据判断继续、补充验证、调整范围或暂缓发布 |
| 资深开发者 | 委派边界、设计约束、差异审查、独立验证、调试恢复 | 委派一个有边界的任务，发现隐藏问题，并说明结果为何可接受 |
| 无编码经验者 | 场景、输入输出、页面、数据、规则、验收与求助 | 完成一个小变更，提供正常与异常用例和验证结果 |

赋能提供分层课程、讲稿、示例和练习；答疑提供可操作的 FAQ 与排查路径；指导提供真实任务接入、评审、验收和复盘模板。培养种子导师分担日常支持，人员与投入待确定。

### 2.1 共同开篇：从三个小失败进入课程

所有分层课程共用约 10 分钟的开篇，先讲困难与案例，再连接方法。首版定位是教学假设，待访谈与试讲校准。

| 受众 | 主要困难 | 开篇小失败 | 引出的第一步 |
|---|---|---|---|
| 主管 | 缺少依据来判断交付状态与作出承诺 | 看到页面进展快，未经评估就承诺新增审批同日交付，试用暂缓，延期说明缺少依据 | 对照原范围、验收状态与变更影响比较可行方案 |
| 资深开发者 | 难以低成本验证 AI 修改是否可信 | 修相邻预约问题时，重叠预约规则及测试预期被一并改错，审查后暂缓合并 | 独立核对业务例子，并审查代码及测试预期变化 |
| 新手 | 不会把想法拆成可操作、可验收任务 | 预约页面可操作，但刷新后记录消失，不知道下一步怎么描述和检查 | 写出具体验收例子，逐项实现与验证 |

详细材料见 [培训开篇](../training/00-opening.md)：虚构案例、可照读讲稿、互动问题、第一步行动、后续课程衔接与试讲检查。讲稿、故障代码和三套 PPT 均已形成，检查见 [验证入口](../evidence/VALIDATION.md)；实际试讲尚未开展。

## 3. 客户场景与需求基线

先了解用户、业务目标、现状流程、痛点、约束与成功标准，明确业务负责人和验收人；用原型或输入输出例子确认理解，再确定本期范围、后续范围、验收条件与外部依赖。

建立“客户目标 → 场景/需求 → 验收条件 → 任务/实现 → 测试与演示证据”的对应关系。每个主要场景包含正常与异常用例，记录假设和待确认项。

能力建设本身也要访谈三类受众，以真实阻塞选择课程与试点；软件试点从代表性客户场景中选择，评估业务价值、数据/环境可获得性、风险和可验证性。客户资料依实际授权使用，教学优先使用虚构或适当脱敏数据。

交付：访谈记录、现状流程、场景卡、原型、范围与验收基线、需求追踪表、依赖清单。当前尚未取得真实客户需求或确认。

## 4. 4A、部署与 DfX

4A 暂按以下四类视图解释；已有部门或客户标准时记录并沿用。

| 视图 | 最小内容 |
|---|---|
| BA 业务架构 | 用户、目标、流程、规则及业务范围 |
| AA 应用架构 | 应用/模块职责、交互关系与外部接口 |
| DA 数据架构 | 核心数据、关系、流向、归属与生命周期 |
| TA 技术架构 | 运行与部署结构、基础组件、技术约束和依赖 |

架构说明包含四类视图之间的对应关系、关键决策、边界、假设与待确认项。保留可编辑图源，提供说明文档和同版本汇报页。通过需求编号与版本关联实现和验收；变更时检查受影响部分。首版深度按案例规模裁剪。

部署与客户对齐：部署位置与开发/测试/生产环境；网络及离线要求；操作系统、计算存储和容器/虚拟机约束；数据库与中间件准入、版本、授权与兼容要求；接口、账号、数据导入迁移；环境提供方及就绪日期；发布窗口、验收环境、监控备份、升级回退与运维分工。形成《部署环境与约束确认表》，本阶段不做具体产品选型比较。

DfX 按场景选择性能、安全性、可靠性、可维护性、可运维性等适用项。需求阶段规划目标/阈值、优先级、责任人、验证方法与环境，并计入计划；与业务、IT、安全及运维相关人员确认取舍；交付《DfX 规划与验收矩阵》、必要设计说明、验证报告及遗留限制/风险记录。矩阵字段为“属性—场景—目标—措施—验证—证据—确认人”。本阶段保持概要，不扩写专题教材。

## 5. 端到端教学案例

已实现入门案例为会议室预约工具：单会议室、每日 09:00—18:00、半小时时间粒度、本地单时区，查看、预约、取消，使用虚构数据。采用 Python 标准库 HTTP、SQLite 和原生网页，案例运行不需要 AI 服务。提供运行说明、21 项测试、故障演练和备份恢复脚本。真实项目实践另选代表性客户场景并确认技术准入。

演示过程：需求澄清 → 验收例子 → 4A 与环境约束 → 分步实现 → 验证失败 → 修复与回归 → 练习环境交付与回退 → 维护复盘。

已标注并实现教学故障演练：相邻时段误判；错误修复连同测试预期一起改变而呈现“全绿”；页面内存模型重建后数据丢失。独立业务验收与真实 SQLite 行为形成对照。并发争抢由实际数据库和 HTTP 测试验证，未声称录制了真实 AI 失误。

追加一场需求变更演练，如从基础预约增加审批，展示需求与架构变化、环境依赖、DfX 验证增量、影响分析、方案比较与承诺调整。演练数字标为教学假设，不作为真实延期依据。

同一仓库分层教学：主管看证据与决策；工程师看设计、代码差异、验证与故障处理；新手看需求到验收，并在导师支持下完成新变更。

## 6. 汇报、进度与成效

建议每周一页状态报告，里程碑安排可运行演示与评审。这是实施建议，当前未创建任何定时任务或对外汇报安排。

能力建设阶段：材料可用 → 试讲通过 → 完成练习 → 独立完成新任务 → 真实项目验证。

软件交付阶段：场景确认 → 方案验证 → 功能验收 → 发布准备 → 客户接受。

报告包含原承诺、当前已批准承诺、已验收成果及证据、剩余工作、阻塞、最新预测、偏差原因、待决策事项/责任人/最晚决策时间。分别显示实现、验证、接受状态；场景数量用来展示状态，工期根据剩余工作和依赖预测。将预测日期与已批准日期分别展示。

成效基线建议记录：交付周期及波动、一次验收通过率、缺陷与交付失败、人工审查/返工时间、验收任务总成本、具备相应能力的人数。说明样本和条件，配合案例分析；当前尚无真实收益数据。

## 7. 需求变更与交付承诺

轻量闭环：登记变化 → 影响分析 → 重新排程 → 提供方案 → 授权确认 → 更新并验证。

变更记录包含来源、业务原因、紧迫性、相对原基线差异和新验收条件。区分新增需求、缺陷、理解偏差、估算偏差与外部条件变化；存在归因争议时仍先分析影响。

分析覆盖已完成工作的返工、架构、代码、数据、测试、联调、部署、文档和培训。工期考虑依赖与关键路径、可并行部分、人员、外部等待和剩余缓冲；用适当区间表达不确定性。新增工作量、人日与实际延期天数分别记录。

比较可行选项：按原日期交付核心范围、完整范围延期、分期交付、替换低优先级功能、增加适合资源。保留必要质量与验收要求，说明每种方案的价值、代价、前提和剩余风险。

由有权限的人确认范围、资源、预算与日期；跨团队依赖由对应负责人确认。记录选择、授权依据、新基线及假设，保留原基线。说明最晚决策时间和等待的影响，未确认事项保持待决，继续未受影响的已授权工作。

对周边沟通共用一份影响分析：客户看价值与范围，主管看资源和风险，上下游看接口与联调日期，研发测试看变更边界和验收条件。
