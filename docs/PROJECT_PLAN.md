# 建设方案：以自学、实践和独立迁移为主

版本：1.1；整理日期：2026-10-04。

状态：本版将已有学习材料组织为“选择问题 → 阅读例子 → 动手实践 → 对照自检 → 独立新任务 → 真实项目评审”。读者可按自己的起点选择路线，随时开始并按成果推进。各产物的制作与验证状态见 [STATUS](../STATUS.md)；材料完成不代表人员已掌握，也不代表真实客户已接受。

## 1. 目标与约束

让部门有依据地委派 AI、验证结果、处理失败，并培养能够承担交付责任的人。这里采用广义工程 harness：任务规范、项目上下文、开发环境、工具权限、自动检查、反馈与恢复机制。AGENTS.md 保存稳定工作约定；需求、架构、代码、检查与决策记录共同支撑可接管的交付。

本项目须满足以下要求：

- 提供可自学的文档、案例代码、PPT、练习与参考答案，支撑赋能、问题排查和必要协作。
- 面向主管、资深开发者和无编码经验者，从三类主要困难与虚构小失败进入同一个端到端案例。
- 对齐客户需求和场景，提供阶段汇报、进度展示与证据链。
- 系统应对需求变化，说明范围、资源和工期影响，支持授权人合理调整承诺。
- 提供 BA/AA/DA/TA 四个架构视图；部署仅列客户对齐事项，DfX 仅简述规划、交流和交付方式。
- 保留可维护源文件、实际验证证据、未确认事项与持续改进记录。

分别评价两层结果：读者能否独立完成新任务；真实软件项目是否满足客户价值与工程交付要求。两者都不能仅以材料数量或代码生成速度判断。

## 2. 三类读者怎样开始

| 读者 | 首要问题 | 学习动作与产物 | 自检标准 |
|---|---|---|---|
| 部门主管 | 怎样看进度、控风险、储备人才和管理工具依赖 | 读周报与变更案例，写一页范围/日期/资源决策卡 | 区分实现、验证、接受；解释预测依据与决策权限，列出接管责任 |
| 资深开发者 | 怎样低成本判断 AI 修改是否可信 | 从需求推导反例，读差异，运行故障与恢复练习，再做一个新变更 | 预期独立于实现；能识别测试一起改错及副作用，留下复核证据 |
| 无编码经验者 | 怎样把想法变成软件任务并验收 | 认识页面、服务端、数据库；写输入输出，启动案例并检查正常与异常行为 | 能重现结果、解释基础关系、区分预期和实测，并描述卡住的位置 |

从[实践入口](guides/README.md)选择一条路线。每条路线给出阅读顺序、操作步骤、完成标准与参考例子；先做自己的判断，再看答案。遇到困难先按[问题排查与协作求助](guides/mentoring.md)完成第一轮检查；需要他人确认时说明具体问题，不要求支持者全程在场。

### 共同起点：三个小失败

| 读者 | 虚构小失败 | 自己先回答的问题 |
|---|---|---|
| 主管 | 看见页面进展快，就答应新增审批同日交付；之后无法解释延期 | 原范围是什么？新增工作改变哪些依赖？谁有权调整承诺？ |
| 资深开发者 | 相邻预约修好了，重叠规则与测试预期却一起改错 | 哪个独立反例能识别错误？测试预期的依据在哪里？ |
| 新手 | 预约页面可操作，刷新后记录消失，不知道从哪里检查 | 输入、规则、保存、查询分别在哪里？怎样写复现步骤？ |

阅读[三个小失败](../training/00-opening.md)，记下初始答案；完成对应实践后再作答并比较变化。案例是学习设定，不能写成真实 AI 失误统计或客户事故。

## 3. 学习过程与可见进度

按成果推进；可重复某一步，也可凭已有能力直接完成对应自检。独立新任务应不同于原样例子，避免把照抄视为迁移。

| 阶段 | 自己要做什么 | 通过检查后得到什么 | 卡住时返回哪里 |
|---|---|---|---|
| 选择问题 | 写出角色、当前困难和预期成果，做一次起始判断 | 个人学习目标与能力基线 | 角色指南、FAQ |
| 理解例子 | 阅读需求、必要架构与角色指南，先推导预期 | 场景卡或业务反例 | 需求边界表、基础概念 |
| 完成实践 | 按说明运行或推演，记录实际过程 | 操作结果、决策卡或代码差异 | 运行说明、排查流程 |
| 对照与修正 | 对照标准和答案，解释差异，修正后再验证 | 有依据的通过/待补结论 | 对应需求、检查与参考答案 |
| 独立迁移 | 换输入、规则或任务，减少逐步提示再做一次 | 新任务及证据、自评和帮助记录 | 自评模板与必要协作 |
| 真实任务评审 | 确认客户场景、环境和责任，完成有限范围任务 | 实际验收、成本和风险记录 | 业务/技术/授权负责人 |

以[能力自评与复盘模板](../templates/capability-pilot.md)记录结果。自评用于定位缺口；真实交付的技术评审、客户接受和权限要求继续执行。当前没有真实自学成效或收益测量，不预先填写通过人数。

## 4. 客户场景与需求基线

先了解使用者、业务目标、现状流程、痛点、约束和成功标准，明确业务负责人及验收人。用原型或输入输出例子确认理解，再确定本期范围、后续范围、验收条件及外部依赖。

建立“客户目标 → 场景/需求 → 验收条件 → 任务/实现 → 检查与接受证据”的对应关系。每个主要场景包括正常与异常用例，记录假设和待确认项。能力建设也应收集三类读者真实的困难与材料使用反馈，用来调整学习路径；不把虚构案例当成已访谈结果。

真实实践优先选择价值可说明、数据与环境可获得、范围可控、结果可验证的场景。客户资料按实际授权使用，自学案例使用虚构数据。交付包括访谈记录、场景卡、范围/验收基线、需求追踪及依赖清单；见[模板](../templates/scenario-baseline.md)和[已填示例](case/requirements.md)。真实客户基线尚未确认。

## 5. 4A、部署与 DfX

4A 暂按以下解释；已有部门或客户标准时记录并沿用。

| 视图 | 最小内容 |
|---|---|
| BA 业务架构 | 用户、目标、流程、规则及业务范围 |
| AA 应用架构 | 应用/模块职责、交互关系与外部接口 |
| DA 数据架构 | 核心数据、关系、流向、归属与生命周期 |
| TA 技术架构 | 运行与部署结构、基础组件、技术约束和依赖 |

[案例架构](case/architecture.md)提供可编辑图源、视图对应关系、关键决策、假设和限制。自己选 R03，依次说明业务冲突规则、服务端职责、数据库约束和运行位置，再用 A03/A08 检查；变更时重新查看受影响视图。

部署与客户对齐：环境位置与开发/测试/生产划分；网络及离线要求；操作系统、计算存储和容器/虚拟机约束；数据库与中间件准入、版本、授权和兼容；接口、账号、数据迁移；环境提供方与就绪日期；发布窗口、验收、监控备份、回退与运维分工。交付[部署对齐表](../templates/deployment-alignment.md)，本阶段不展开产品选型比较。

DfX 按场景选择性能、安全性、可靠性、可维护性、可运维性等属性，在需求阶段规划目标/阈值、优先级、责任人、验证方法及环境，纳入计划并与相关人员确认取舍。交付[简明矩阵](../templates/dfx-matrix.md)、必要设计说明、验证证据和遗留限制。本地小规模测试不得外推为生产保障。

## 6. 端到端实践案例

案例为会议室预约工具：单会议室、所选日期内 09:00—18:00、半小时时间粒度、本地单时区，支持查看、预约、取消与持久化；使用虚构数据。采用 Python 标准库 HTTP、SQLite 和原生网页，运行案例不需要 AI 服务。已有运行说明、21 项测试、故障练习和备份恢复脚本，实际检查见[验证入口](../evidence/VALIDATION.md)。业务基线保持不变，午休限制和审批均未实现。

按这条链自己完成实践：需求澄清 → 验收例子 → 4A 与环境约束 → 分步实现 → 检查失败 → 修复与回归 → 本机交付与恢复 → 复盘。主管可重点推演进度和决策；工程师重点运行、审查与修复；新手先完成场景和手动验收，再尝试小变更。

故障脚本预设相邻误判、错误修复连同测试预期一起改变而“全绿”、页面内存重建后数据丢失，用独立业务验收与真实 SQLite 行为对照。它们不是已记录的真实模型行为统计。并发争抢由实际数据库与 HTTP 测试验证，证据范围以记录为准。

新增午休限制用于练习小变更；新增审批用于练习架构影响、环境依赖、验证增量、方案比较及承诺调整。练习在独立副本中进行，假设写清楚，不能据此修改真实客户基线或声称生产可用。

## 7. 阶段汇报、进度与成效

个人学习可在每次产出后更新自评；组织可按约定周期汇总独立任务表现与实际阻塞。真实软件项目建议用一页状态报告，并在里程碑展示客户场景和验收证据。这里不创建定时任务或对外汇报安排。

能力进度：理解例子 → 完成实践 → 自检修正 → 独立新任务 → 真实任务评审。软件进度：场景确认 → 方案验证 → 功能验收 → 发布准备 → 客户接受。两类状态分别报告。

[报告](../templates/weekly-milestone.md)包含原承诺、当前已批准承诺、已验收成果与证据、剩余任务、阻塞、最新预测、偏差原因及待决事项/责任人/最晚决策时间。分别显示实现、验证和接受；场景数量展示覆盖，工期按剩余工作和依赖预测；批准日期与预测日期分列。

成效记录可比任务的交付周期与波动、一次验收通过率、缺陷/交付失败、审查返工时间、验收任务总成本及具备相应能力的人数。说明样本与条件，未测量项明确标注。读完材料或生成代码快都不能单独证明收益。

## 8. 需求变更与交付承诺

轻量闭环：登记变化 → 影响分析 → 重新排程 → 提供选项 → 授权确认 → 更新并验证。

记录来源、业务原因、紧迫性、原基线差异和新验收条件；区分新增需求、缺陷、理解偏差、估算偏差及外部条件变化。有归因争议时仍先收集事实、分析影响。

影响覆盖已完成工作的返工、4A、代码、数据、测试、联调、部署、文档与使用说明。工期考虑依赖及关键路径、可并行部分、人员日历、外部等待和剩余缓冲；用适当区间表达不确定性。新增工作量、人日与实际延期天数分别记录，不能直接换算。

比较原日期交核心范围、完整范围延期、分期、替换低优先级项、增加适合资源等方案；保留必要质量与验收，说明价值、代价、前提和风险。由有权限的人确认范围、资源、预算和日期，跨团队依赖由相应负责人确认；保留原基线和书面决定。未确认保持待决，继续未受影响的已授权工作。

[审批案例](case/change-example.md)在明确假设下推演 D10 → D12—D14，不是实际延期许可。客户看价值和范围，主管看资源与风险，上下游看接口和联调日期，研发测试看边界和验收，使用同一份影响依据。

下表描述材料用途和验收要求；每项当前制作、发布与实际验证状态以 [STATUS](../STATUS.md)为准。不能由材料存在推断读者已经学会或客户已经确认。

| 编号 | 交付包 | 主要产物 | 可独立使用的完成标准 |
|---|---|---|---|
| D01 | 项目基础与持续改进 | README、AGENTS、方案、状态、改进记录 | 入口可用，要求可追踪，已完成与未验证区分清楚 |
| D02 | 客户需求 | 场景模板、已填范围/验收基线、需求追踪 | 能照例编写新场景，假设与真实确认分开 |
| D03 | 架构与运行质量 | 4A 图源/说明、部署表、DfX 矩阵 | 视图与代码一致，能追踪一条需求并说明限制 |
| D04 | 主管学习 | 困难案例、指南、PPT、周报与能力模板 | 能独立比较范围/日期/资源方案并给出依据 |
| D05 | 工程师实践 | 指南、PPT、任务卡、故障练习及答案 | 能委派有边界的任务、复现问题并独立验证 |
| D06 | 新手起步 | 基础概念、指南、PPT、操作练习及答案 | 能启动、写例子、记录实际结果、定位或描述阻塞 |
| D07 | 案例工程 | Python/SQLite/网页、测试、故障与恢复脚本 | 可运行、可复现、可验证、可恢复 |

| D09 | 进度与变更 | 模板、已填案例、依赖与延期分析 | 原/新承诺、预测、依据、权限和待决清楚 |
| D10 | 验证与迁移 | 工程/材料检查、自评及真实任务复盘 | 实际执行有记录，独立迁移与真实效果另行验证 |

代码、图源、文档和 PPT 使用一致案例与编号，保留可维护源文件。材料维护由建设负责人统筹；真实客户、技术和授权职责由实际项目指定。协作答疑可按需求安排，不是开始自学的前置条件。

## 10. 真实项目接入与持续改进

可立即执行：选择角色路线，运行本地例子，完成练习和自检，再换一项小任务。只有依赖真实组织信息的事项才等待确认：业务/客户场景、现有 4A 口径、工具和技术栈准入、部署约束、实际人员资源、验收与决策权限、日期和成本边界。

从真实任务收集卡点、验证结果、人工审查/返工及工具不可用时的接管表现，用证据决定下一轮材料修改和推广范围。遇到学习步骤不清楚，记录具体页面、操作、预期和实际；修订后由独立读者重做相应步骤。真实学习反馈尚未收集，不能预填成效。

实际进展见 [STATUS.md](../STATUS.md)，反馈处理见[改进记录](IMPROVEMENTS.md)。
