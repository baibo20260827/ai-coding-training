项目工作约定

目标与适用范围

本项目建设部门的软件工程 harness 与 AI coding 能力，以自主学习和动手实践为主要使用场景，支撑日常答疑、项目指导和持续改进。交付物包括可维护文档、可运行代码、PPT、练习、模板和验证证据。

默认直接面向学习者写作，不模拟讲师授课。每条学习路径说明起点、阅读顺序、操作步骤、预期结果、自检标准和遇到困难时的查阅入口。材料应能在没有讲师在场时使用；PPT 备注用于补充解释，不写讲师台词、课堂动作、举手互动或固定授课节奏。需要协作求助、技术评审或客户确认的事项仍明确责任人，不能以自学完成代替真实交付审批。

同时关注两层结果：本次能力建设是否使团队学会，以及团队使用 AI 交付的软件是否满足客户需求。按任务规模裁剪流程，保持必要证据。

本文件保存长期有效的工作原则与阅读入口。具体方案、任务状态、客户承诺和逐次反馈保存在关联文档中，避免将本文件扩成知识库或工作流水账。用户最新的明确指示优先；在已授权范围内自主推进可逆的本地整理与验证。

开始与结束工作

  1. 开始时阅读 README.md 与 STATUS.md，了解项目入口、真实进展和当前任务。
  2. 按任务读取 建设方案 的相关部分；涉及反馈、复盘或规则调整时读取 改进日志。
  3. 区分用户明确要求、工作假设、方案建议、客户已确认基线和实际验证结果。缺少的信息标为待确认；合理假设应说明，不得包装成已确认事实。
  4. 结束时更新真实进展、产物路径、验证结果、未解决问题和下一步。新反馈需要登记改进记录，并说明是否已验证效果。

三类受众与三种用途

  • 部门主管：覆盖进度控制、风险控制、人才储备与培养、工具依赖和交付责任；材料应支持实际决策。
  • 资深开发者：将对 AI 行为的质疑转化为任务边界、设计约束、差异审查、独立验证和失败恢复；用可重复证据建立信任。
  • 无编码经验者：从用户场景、输入输出、页面、数据、业务规则和验收起步，逐步学习软件基础；明确求助与技术交接方式。

赋能材料应有学习目标、示例和练习；答疑应有适用场景、排查步骤及验证方法；指导应能在真实任务中复用。考核应包含未原样讲过的小变更或故障，观察独立处理能力。

自学入口以三类受众各自的主要困难和一个典型小失败开篇，先帮助读者认出问题，再引出方法。每个案例包含期待、行动、可见后果、困难、一项可执行的下一步及相关阅读。虚构或合成案例明确标注，主要困难的定位根据读者反馈与实践结果校准；避免责备读者或将一次示例推广为 AI 的普遍表现。完整案例维护在 三个小失败。

客户需求与交付主线

围绕“客户场景 → 需求与验收基线 → 架构与计划 → 小步实现与验证 → 阶段演示 → 客户接受与维护”组织交付。

  • 明确实际使用者、业务负责人、验收人、业务目标、正常与异常流程、范围边界、约束和外部依赖。
  • 开发前用原型或具体输入输出例子核对需求理解，定义可观察、可验证的成功条件。
  • 建立“客户目标 → 场景/需求 → 验收条件 → 任务/实现 → 验证证据”的追踪关系。
  • 保留已确认范围、验收条件和计划的版本。需求、实现、测试和培训材料发生变化时检查关联内容。

4A、部署与 DfX

  • 4A 暂按业务架构 BA、应用架构 AA、数据架构 DA、技术架构 TA 解释；客户或部门有既定口径时以其为准并记录。
  • 架构交付应有四类视图、视图间的对应关系、关键决策、边界、依赖及待确认项。提供可编辑图源与说明，汇报内容保持同版本。深度与项目规模匹配。
  • 部署只保留客户对齐清单：部署位置及环境、基础设施约束、数据库与中间件准入/版本/授权、数据与系统连接、环境提供方及就绪日期、交付与运维分工。
  • DfX 按场景规划性能、安全性、可靠性、可维护性、可运维性等适用属性，明确目标/阈值、优先级、负责人、验证方法与环境、验收证据和遗留限制。
  • 当前建设材料中，部署与 DfX 保持简要，聚焦如何规划、交流和交付；未经用户进一步要求，不扩写成详细选型或专题教材。

进度、汇报与变更

  • 分别报告材料/工具产出进度与人员能力效果。软件交付按可验收成果和里程碑展示，并区分已实现、已验证和已接受。
  • 阶段报告包含：原承诺、当前已批准承诺、已验收成果及证据、剩余工作、阻塞、最新完成预测、偏差原因和待决策事项。
  • 将当前预测日期与已批准承诺日期分别展示；发现偏差及时说明依据、假设和不确定性。
  • 变更采用“登记 → 影响分析 → 方案比较 → 授权确认 → 更新基线 → 执行与验证”的流程。小澄清轻量记录；影响范围、成本、里程碑或验收条件的变化进入正式评估。
  • 区分新增需求、缺陷修复、理解偏差、估算偏差和外部阻塞。影响分析覆盖返工、设计、代码、数据、测试、联调、发布和材料维护。
  • 工期评估考虑任务依赖、关键路径、可并行工作、人员可用性、外部等待及可用缓冲。新增人日不能直接等同于延期天数；估算保留适当区间与前提。
  • 提供维持日期调整范围、完整范围延期、分期交付、替换低优先级项或增加适合资源等可行选项，保留必要质量与验收要求。
  • 对外范围、预算与日期承诺由有相应权限的人确认，AI 提供评估与沟通草稿。保留确认依据和原基线；待决事项不写成已批准。继续推进不依赖该决定的已授权工作。

工程与教学证据

  • 优先采用短任务、清晰边界、可审查变更和可重复检查。按项目风险确定验证力度，记录实际运行的命令、环境、结果和限制。
  • 不编造测试通过、客户确认、培训反馈、收益数字、工期、演示截图或运行日志。未执行的检查明确标记；测试通过不等于客户接受。
  • 教学故障采用明确标注的故障版本或步骤稳定复现，展示发现、定位、修复、回归与恢复过程。教学假设与真实试点数据分别标明。
  • 示例交付包含运行方法、依赖说明、验收用例、验证方法和恢复说明。实际运行/检查命令以 案例 README 为准，结果以 验证记录 为准；修改后按影响范围重新验证，不沿用失效结论。
  • 文档说明适用对象、使用方式和完成标准；PPT 提供可编辑文件、逐页阅读补充、动手任务和自检提示，并检查渲染可读性；图源、代码、文档和课件保持一致。
  • 关键质量要求通过实际测试与检查落实；访问边界通过实际权限配置落实。写入 AGENTS.md 只提供工作指导，不能替代这些机制。

持续改进

每次用户反馈、自学问题、试点故障或工具变化，按以下闭环处理：

  1. 记录来源、日期、问题或新增要求及适用场景。
  2. 分析受影响的受众、需求、架构、代码、文档、PPT、模板及验证方式。
  3. 在已授权范围内落实改进；涉及对外已确认承诺的调整，走对应变更流程。
  4. 验证修订内容；需要真实学习记录或客户反馈才能验证的事项保持待验证。
  5. 在改进日志记录变更位置、结果、遗留问题和下一步；同步状态与交付索引。
  6. 将具有普适性、长期有效的经验提炼到本文件；案例细节、阶段状态和问题历史保留在各自文档。

衡量改进时关注交付周期、一次验收通过率、缺陷与交付失败、审查与返工时间、验收任务总成本和相应能力人数。记录基线、样本范围和条件，避免由小样本过度推断；代码量、AI 生成占比或使用次数不单独作为成效依据。

  • 产物存在且入口可用，状态与实际一致；相关文档和改进记录已同步。
  • 适用的检查已完成并留下证据；未执行项、待确认项和限制清楚可见。
  • 不将方案完成、材料完成、工程验证完成、培训有效和客户接受混为同一状态。
