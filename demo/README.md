# 会议室预约：可运行的 Harness 教学案例

版本：1.0，2026-10-03。适用对象：讲师、工程师、新手及查看交付证据的主管。

本案例把“客户场景 → 验收例子 → 设计 → 实现 → 失败定位 → 回归 → 交付与恢复”连起来。数据和业务情境均为虚构教学用途；实现与测试已形成，客户接受和培训效果尚待真实参与者验证。

## 5 分钟启动

1. 将完整项目保存到本机，打开终端并进入项目根目录。确认 `python3 --version` 可用；代码兼容 Python 3.9+，实际使用组织准入且仍受维护的 Python 3 版本。无需 `pip install` 或 `npm install`。
2. 从项目根目录执行：

   ```sh
   python3 demo/app.py --port 8765
   ```

3. 在浏览器打开 [本地教学页面](http://127.0.0.1:8765)。保持终端运行，用虚构姓名建立预约。结束时在终端按 `Ctrl+C`。

Windows 可将所有命令中的 `python3` 替换为已安装的 `py -3`，例如 `py -3 demo/app.py --port 8765`。这是操作路径说明，当前实测环境为 macOS，Windows 尚未实测。若机器没有 Python，由组织提供符合准入要求的安装；不要求新手自行更改安全策略。

默认数据库位于 `demo/data/bookings.sqlite3`，首次启动自动建立；停止和重启服务不会删除它。不要双击 `index.html`，页面需要连接本地 HTTP 服务。每条预约只包含一个日期；日期初值取本机当天，不做跨日或时区换算。

再次练习需要空数据时，选择一个**全新数据库文件名**，保留原数据：

```sh
python3 demo/app.py --port 8765 --db demo/data/session-02.sqlite3
```

端口占用时先停止自己已启动的实例，或将端口与访问地址一同改为 8766；不要终止不认识的进程。若沙箱拒绝监听本机端口，需要允许本地预览的执行环境；这与应用测试失败应分别记录。

## 基线行为

- 单会议室，每天 09:00–18:00，以 30 分钟为粒度；不限制日期必须在未来，便于稳定复现教学用例。
- 查看当日预约，提交姓名、主题和起止时间，取消预约。
- `10:00–11:00` 与 `11:00–12:00` 相邻允许；与 `10:30–11:30` 重叠拒绝。
- 数据写入 SQLite，浏览器刷新和服务重启后保留；取消后释放时段。
- 并发竞争同一时段时最多一条成功；没有容量测评或高并发服务承诺。
- 仅绑定 `127.0.0.1`，不含登录与审批。本机操作者可看到并取消全部教学记录，不能把此行为当作正式权限方案。

## 检查与演练

```sh
python3 -m unittest discover -s demo/tests -v
python3 demo/labs/failure_lab.py
python3 demo/backup.py exercise
```

测试使用临时数据库和临时回环端口，结束自动清理。故障脚本展示“相邻误拒 → 错误修复与弱测试全绿 → 独立验收发现 → 正确规则及主应用通过”，同时模拟页面内存重建与数据库重新连接的差别。它不修改主应用，也没有故意让正式测试误报通过。脚本退出码 0 表示**预设故障被如期发现、正确实现通过**。

备份/恢复演练只在自动清理的临时目录中运行，演示恢复到新文件与拒绝覆盖已有文件。实际执行结果和环境限制见 [验证记录](../evidence/demo/VALIDATION.md)。

## 接口与结构

| 接口 | 输入 | 正常结果 | 主要异常 |
|---|---|---|---|
| `GET /api/health` | 无 | 200，运行模式与 schema 版本 | 仅做 HTTP 存活检查，不证明数据/业务全部正常 |
| `GET /api/bookings?date=YYYY-MM-DD` | 一个日期 | 200，`{"bookings": [...]}`，按开始时间排序 | 400 日期非法或缺失 |
| `POST /api/bookings` | `application/json`，见下例 | 201，`{"booking": {...}}` | 400 非法输入、409 冲突、413 大小、415 类型、503 数据库不可用 |
| `DELETE /api/bookings/{id}` | 32 位预约 ID | 200，`{"cancelled": true}` | 404 不存在、503 数据库不可用 |

```json
{"date":"2026-10-08","start":"10:00","end":"11:00","name":"演示同事 A","purpose":"需求验收练习"}
```

错误结构：`{"error":{"code":"booking_conflict","message":"该时段已被预约，请刷新列表并选择其他时段。"}}`。如果提交期间连接中断，先刷新确认是否已经保存，再决定重试。

数据库的 `bookings` 保存预约；`slots` 为预约占用的每个半小时建立一行，主键 `(day, start_minute)`。`BEGIN IMMEDIATE` 将创建操作串行进入事务；预约及其全部时段在一个事务内写入，唯一约束拒绝重叠，失败回滚全部写入。取消通过外键级联释放时段。代码中的 `overlaps()` 用于教学对照；实际一致性保证来自数据库事务与约束。

## 备份、恢复与代码回退

先确定当前 `--db` 的真实路径。使用从未存在过的目标文件名；下列名字仅作为一次演练示例：

```sh
python3 demo/backup.py backup --source demo/data/bookings.sqlite3 --output demo/backups/before-change.sqlite3
python3 demo/backup.py restore --source demo/backups/before-change.sqlite3 --output demo/data/restored.sqlite3
```

备份调用 SQLite backup API，检查应用标识、schema 版本和数据库完整性。恢复也只写入全新文件，不覆盖当前库。然后停止原服务，在新路径启动并验证：

```sh
python3 demo/app.py --port 8765 --db demo/data/restored.sqlite3
```

比较快照时间、预约条数和目标记录，确认满足预期后才将新路径作为后续教学环境。**恢复到旧快照不会保留快照后的修改**；原数据库仍留存，必要时可停止服务并重新指向它。脚本不迁移 schema，也不合并两份数据。

代码回退与数据恢复分别处理：开始练习前保留本项目的已验证副本或自己批准的 Git 版本；变更失败时停止服务，用新的工作目录取出该版本，运行检查，再用兼容数据库启动。不要对未知工作区执行 `reset --hard`，不要假定旧代码兼容新 schema。本版故障演练不改主应用，因此无须实际回退代码。

## 完成标准与限制

案例工程完成标准：上述检查通过；他人能按说明启动、复现预设故障、验证正确行为、恢复到新文件，并说清证据的适用范围。实际界面操作情况见验证记录，自动测试不能替代真实客户验收。

部署环境、数据库准入、备份责任和 DfX 目标仍需与真实客户对齐。本案例选择 SQLite 只是为了本地无外部依赖教学，不构成客户选型结论。未实现身份认证、审批、生产运维、高可用、跨时区、迁移流程或性能容量承诺。真实项目需要另外确认这些范围与责任。
