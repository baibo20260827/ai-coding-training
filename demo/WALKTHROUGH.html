独立完成会议室预约的端到端实践

版本：v1.1。日期：2026-10-04。配合需求追踪与运行说明操作。本次文档更新不改变应用基线；以下步骤可以分多次完成，用自己的记录衔接。

目标：你能把需求、设计、操作结果、自动检查和恢复联系起来，解释哪些结论已有证据，以及哪些仍需进一步验证。

1. 准备数据与记录

使用完整项目目录、组织准入的 Python 3 和浏览器。命令在项目根目录执行；Windows 入口、数据库位置及端口问题见README。修改代码前保留已验证副本。

只用虚构姓名和主题。下面统一选 2026-10-08；应用不限制只能预约今天。若该日期已有不属于本次练习的记录，选择一个全新的 --db 文件名，不删除或取消不认识的记录。把本轮日期和数据库路径记下来，刷新或重启后仍使用它们。

准备一份操作记录，每行包含：需求编号、操作与输入、预期、实际结果、证据位置、未解决事项。预期可以提前写，实际结果只在执行后填写。

完成本步时： 你知道使用哪份项目、哪一天、哪个数据库，并能区分已有工程验证记录与本次自己的操作结果。

2. 将一句话需求展开为验收例子

阅读 R01–R08，特别关注 A03 相邻与冲突、A05 刷新和重启后保留、A08 同时预约的一致性。自己先写出三个例子，再比较下面的规则：

  • 单会议室、09:00—18:00、半小时粒度，起止时间在同一天。
  • 已有 10:00—11:00 时，11:00—12:00 允许，10:30—11:30 拒绝。
  • 成功记录需要保存；取消后时段释放；并发也应遵守不重叠规则。

当前案例没有登录和审批。新增审批应进入需求变更分析；不能用尚未实现的新增功能否定已经完成的原范围，也不能仅看页面就认定原范围全部通过验收。

自检： 你能为每个例子写出具体输入和可观察结果吗？哪些要求需要实际操作、自动检查或客户确认，无法仅从截图判断？

3. 启动并逐项验证

在终端执行：

python3 demo/app.py --port 8765

需要隔离新一轮数据时，使用 --db demo/data/self-study-01.sqlite3，且确认此文件名尚未存在。终端显示的数据库路径是本次持久化的依据。保持服务运行，在浏览器访问 http://127.0.0.1:8765。

按顺序操作，在记录中填入自己的结果：

操作 预期观察 对应
日期选 2026-10-08，使用虚构信息预约 10:00—11:00 成功，列表出现准确时段、姓名与主题 A01/A02
刷新浏览器，再选择同一日期 预约仍存在；页面默认日期可能回到当天，要先核对日期 A05
预约 11:00—12:00 成功，相邻允许 A03
预约 10:30—11:30 提示冲突，列表没有新增记录，已有两条仍在 A03
点击第一条的“取消预约”，先选“保留预约” 第一条仍保留 A04
再次取消第一条，选择“确认取消” 10:00—11:00 的记录消失 A04
重新预约 10:00—11:00 成功，表明原占用已释放 A04
将结束时间选到开始时间之前并提交 提示明确，数据库不增加记录 A06

预期与实际不一致时，先保留操作步骤和提示，检查日期、数据文件、时间规则和当前服务状态。不要把重做后成功掩盖成第一次就成功，也不要为了得到绿色结果降低验收要求。

自检： 能否解释刷新和取消重订各在验证什么？当前单浏览器操作还没有覆盖全部并发与运行边界。

4. 验证停服提示与重新启动

  1. 保留页面，在启动服务的终端按 Ctrl+C，确认自己启动的进程已停止。
  2. 在页面尝试新增一条尚未占用的时段，例如 14:00—14:30。预期显示连接失败，不能出现成功写入的提示。
  3. 使用刚才相同的命令和数据库路径重新启动服务。
  4. 刷新页面并重新选择 2026-10-08。预期先前成功建立的记录仍在，停服时失败的那条没有出现。
  5. 如需验证取消也持久化，取消一条本轮记录，再停止、重启并查看同一日期；它应继续保持已取消。

自检： 本步支持 A05 持久化和 A07 停服时不假报成功的部分结论。若提交瞬间连接中断而不是明确停服，先刷新核对是否已经保存，再决定重试。

5. 发现“测试全绿但规则错了”的预设故障

在另一个终端执行：

python3 demo/labs/failure_lab.py

对照输出，逐项解释：

  1. 旧实现把时间当闭区间，错误拒绝相邻预约。
  2. 错误修复只判断两段时间完全相同，还把一条重叠测试预期改成允许，所以弱测试 3/3 通过。
  3. 从需求基线独立取出的验收例子发现部分重叠和包含时段被错误放过。
  4. 正确区间规则通过 4 条例子；主应用的实际 SQLite 操作也做到相邻允许、重叠拒绝。
  5. 页面内存模型重建后 0 条，重新连接持久化数据库仍有 2 条。这是模型模拟，真实浏览器刷新已经在前面单独检查。

这些错误是显式预置的学习材料，不是某次模型行为记录。脚本退出码 0 表示故障被如期发现、正确实现通过，不能解读成错误实现可接受。脚本使用临时数据，不改动主应用。

保存产物： 一条被改错的测试预期、它应依据的业务规则，以及你的独立验收例子。可读 old_conflict、wrong_fix、ACCEPTANCE 对照判断；更完整的边界练习见 L3。

6. 看清约束怎样实际生效

执行：

python3 -m unittest discover -s demo/tests -v

记录实际测试数量、结果和错误。测试使用临时数据库和回环端口，不要求预先启动主应用。已有验证记录可作为排查参照，不能直接复制为自己的检查结果。

主应用把 10:00—11:00 转成 10:00、10:30 两个半小时占用槽，11:00 的槽仍可用于下一条预约。创建时在一个事务中插入预约及其全部占用槽，唯一约束拒绝重复占用；失败整笔回滚，取消通过级联删除释放时段。

数据库和 HTTP 并发检查验证了这类行为。检查运行得快不能证明生产容量，测试通过也不等于客户接受。AGENTS.md 提供工作指导，实际约束仍由事务、权限和检查等机制落实。

自检： 你能否指出一条测试对应的需求，以及该测试不能证明什么？工程师还应说明无事务“先查再插”为何存在竞争窗口；新手可以先画出一条预约对应多个占用槽的关系。

7. 练习备份、恢复与接管

先执行隔离演练：

python3 demo/backup.py exercise

预期：备份有 1 条预约，取消后原库为 0 条，恢复到新文件后为 1 条；原库保留，覆盖已有目标被拒绝。实际操作在自动清理的临时目录完成。

再决定是否对自己的练习数据库操作。需要时按README 的备份恢复步骤确认源路径、使用全新目标名，并记录快照时间与应用/schema 版本。恢复到旧快照不包含快照之后的修改，原库应保留以便核对。

代码回退与数据恢复分别处理。若曾修改独立练习副本，用预先保留的已验证版本恢复代码，再用兼容数据库运行检查；不要对不熟悉的工作目录执行破坏性清理。

自检： 下次重新打开项目时，仅看你的记录能否找到启动、验证、恢复和未解决问题？可继续完成 L6。

8. 把操作结果转成自己的判断

你的学习方向 留下一项可复用产物
主管 一段区分已实现、已验证、待接受的状态说明，以及支撑下一次承诺还缺的信息
工程师 本次接受或退回的结论、独立反例、检查范围与恢复方式

对照自检参考解析，把结果标为已独立完成、借助帮助完成或尚未验证。下一步可以选择午休变更 L4，或新增审批的管理练习 L5；它们都是新增需求，当前基线尚未实现。
